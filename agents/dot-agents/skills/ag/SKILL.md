# Ag

## Ag machines (ag-mac, ag-client, ag-engine, ag-phone)

Load the **`ag-machine-ops`** skill for connection details, Keychain items, MCP re-auth recipes, 1Password vault IDs, and computer-use setup. The essentials:

- **Ag** (Always Generating) is the user's whole agent system. Its machines: **ag-engine**, rented Linux (AWS EC2, us-east-1) and the **session host**: every session (tmux via `ag-mux`), every Ag service, and the repos live there (ag-mac's old home path is a symlink to it, so paths from before the move still work); **ag-mac**, the always-on Mac Ag drives for computer use and Mac-only apps and CLIs (the "extremity"); **ag-client**, the Mac the user sits at (CLI work there: `ag-client run|push|pull|status`, never raw `ssh`/`scp`); and **ag-phone**, their iPhone. Links use the machine-independent address `ag` (a Tailscale Service: `http://ag:7376`, …), never a machine name. Model inference goes through TrueFoundry. `machines/README.md` in the ag repo is the inventory (`ag-host` prints the session host); design in `docs/ag.md` and `docs/ag-mux.md`.
- **From the engine, reach the Mac with `ag-mac`:** `ag-mac run <cmd>` (Mac-only CLIs, Xcode, Keychain; never for the screen: anything that clicks or types is a job on the screen queue, via `ag cua` or `ag screen exec`, with secrets typed inside the job by `ag-type-secret op://…`), `ag-mac push <local> [remote-path|dir/]` / `ag-mac pull <remote> [local-path|dir/]` (files: an exact path, or into a directory; never raw `ssh ag-mac 'cat > …'` or `scp`), `ag-mac show <file|url>`, `ag-mac status`. Call it the moment a task needs macOS; don't move whole sessions to the Mac. Its twin **`ag-client`** (`run`/`push`/`pull`/`status`; login shell, so Homebrew is on PATH) is for work that exists only on the client Mac (its files, a YubiKey on its USB, its app logs); use it instead of raw `ssh ag-client`/`scp`, and never for its screen (that's `ag cua --client --why …`). The shared MCP gateway runs on the engine (`ag-mcp-gateway.service`), so MCP needs no sign-in per session.
- **Computer use: one command, `ag cua "<task>"`** (in Pi, the `ag_cua` tool). It routes for you: ag-mac's desktop by default (queued one run at a time, so check `ag cua --status` before assuming a slow run failed), `--client --why "…"` for the client Mac and `--phone --why "…"` for his iPhone (iPhone Mirroring), both gated last resorts. Don't call `ag-chatgpt-cua`, `ag-mac cua`, `ag-client-cua` or `ag-screen-queue` directly; they're its internals.
- **Secrets:** `op-ag` reads/writes the canonical arcade.school vault; `op-shared` reads/writes the user's everyday personal credentials; `op-work` reads/writes non-super-secret work items (the work card, infra API tokens such as the Tailscale OAuth client; store new work infra tokens there). Vault IDs and item locations are in the private notes (`~/ag-personal/ag-private.md`). Pipe secrets straight into the process that needs them (`op-ag run`/`op-ag read`); never print them into output, logs, arguments, or dotfiles. The engine has `op-ag` and `op-work` but deliberately not `op-shared` (the user's personal vault): from the engine use `ag-mac run op-shared …`. Banking, tax, medical, identity, recovery codes, private keys and primary accounts are deliberately out of reach: ask the user, never go around it through the 1Password app or browser.
- **Programmatic first, on ag-engine first; driving the client's desktop is an antipattern.** Use an API, CLI, or MCP tool whenever one exists. When a task needs a service Ag can't reach yet, your first move is to add programmatic access to it (an API key or token in the vault, a CLI, an MCP server, a small script in ag) that runs **on ag-engine**; only if it truly can't run there (macOS-only app or CLI, Keychain, a Mac-bound login) add it **on ag-mac** behind `ag-mac run`; computer use comes after both, and then only to build that access. Computer use runs on ag-mac (`ag cua` / the `ag_cua` tool). Drive the client only when the task truly exists only there (see the skill for the tool and its `--why` rule); a Jev guard blocks unjustified client automation, so don't route around it. When you must use the client, use it to build capacity (mint the missing API key into the vault once), then work programmatically.
- **Permission dialogs:** on ag-mac, agents' macOS permissions all belong to `sshd-keygen-wrapper` (their TCC identity); run `ag-access` to check them and `ag-access allow` to answer a pending prompt (more reliable than CUA, whose clicks those prompts swallow). Otherwise, when a task stalls on a likely permission prompt or system dialog, grant it yourself with computer use on the machine showing it, then confirm the step proceeds. Ask first only if it grants more than the task needs, authorizes something destructive, or needs a secret the task doesn't already authorize.
- **Tell the user what ag needs.** If something on an Ag machine is missing, expired, or under-permissioned, fix it yourself when it's safe, capture the fix in ag (or dotfiles, for personal config), and tell them. If it needs them (a login, a broader grant, a new secret), stop and ask clearly and kindly; don't silently work around it or drop the task.

## Machine setup lives in git: ag and dotfiles (infrastructure as code)

Every change to the machine setup (any computer, phone, device, or service in the stack) must be captured in git in the same task, committed, pushed, and synced to **every machine** in `machines/README.md`, so any machine could be rebuilt from the two repos alone. Never leave hand edits outside them or commit secrets.

- **ag** (`~/ag`, public `<owner>/ag`): the agent system. tmux (ag-mux) and Pi config, ag-dash, the inbox, ag-presence, the client ↔ host bridge, computer use, `op-*`, Tailscale, infra, LaunchAgents and systemd units, Hammerspoon's agent glue (`ag.lua`), these instructions (`agents.md/`), and the skills.
- **dotfiles** (your public dotfiles repo; checkout per machine in `machines/README.md`): personal machine config. Shell, editor, terminal, git, window management, Brewfile, macOS defaults, per-machine snapshots.

- **ag-personal** (your private personal repo, `~/ag-personal`): the user's personal layer. `AGENTS.md` (linked as `~/AGENTS.md` and `~/CLAUDE.md`, so every agent under the home directory loads it) `ag-private.md` (rarely needed specifics: vault IDs, IPs, accounts), and `env` (private values public scripts read, e.g. `AG_TEXT_NUMBER`). Sync with `ag sync personal`.

**ag and dotfiles are public: nothing personal goes in them.** No addresses, phone numbers, emails, cards, vault IDs, IPs or the tailnet name, teammates' or students' details, employer-internal specifics, or real session content (fixtures included). Write them generically and put the specifics in ag-personal. Check the diff before committing.

When in doubt, it goes in ag. **Load the `dotfiles-change` skill before making the change**: it has where things go, the sync steps, and the host/client model (read it before touching shortcuts, the tmux config, Hammerspoon, or anything that spans the host and a client).

## Client ↔ host bridge (screenshots, viewing, phone)

The user sits at a client machine (and sometimes their iPhone); you run on the session host (ag-engine; `ag-host`). Details are in ag's docs/reference.md, section "Client ↔ ag bridge" (ag there means ag-mac). The helpers default to the current client (`ag-client`); if the user is on a different client, point them at it (`SHOW_CLIENT`, `SHOT_CLIENT`, `CLIENT_CUA_HOST`) or ask which one they're using.

- **Showing the user things is automatic.** Whenever you produce or find something visual for them (image, chart, PDF, HTML page, report, or a running dev server/preview), open it on their screen yourself with `ag-show <file>` (HTML pages bring their local img/css/js along; `ag-show <dir>` opens its `index.html`) or `ag-show http://$(hostname -s):<port>` (the machine the session runs on), then tell them what you opened. Don't open Markdown files on their desktop (`ag-show` skips them and only prints the phone link). Don't make them ask, run a command, or copy a path. Bind dev servers so the client can reach them (e.g. `--host 0.0.0.0`) and use `http://ag-mac:<port>`. If a flow needs literal `localhost` (OAuth callbacks, secure-context APIs), set up an SSH port forward from the client for that task.
- **Screenshots from the user** usually arrive as pasted image paths under `~/inbox/clipboard/` (Hammerspoon uploads them on Cmd+V), or from the phone under `~/inbox/phone/`. Read those paths directly. A just-pasted path appears instantly but its upload can take a second or two over a relayed connection; if the file isn't there yet, wait for it (e.g. `for i in $(seq 20); do [ -f "$p" ] && break; sleep 0.5; done`) instead of saying it's missing. If they mention a screenshot without pasting one, run `ag-shot` (or `ag-shot N`) to pull their newest CleanShot captures into `~/inbox/shots/`.
- **Link to other sessions** with `ag link [session]` (the session's T3 thread when it has one, `ag link --app` for the in-app `t3-thread://` form to paste in a T3 reply; else its ag-dash link); see "Helper sessions and links" under Sessions.
- **Reviewing from the phone.** For HTML pages, folders, and Markdown, `ag-show` also publishes a phone copy and prints `phone: http://ag.<tailnet>.ts.net:7374/r/<name>/` (Markdown is rendered to HTML). Put that link in your message on its own line so the user can tap it on their iPhone (e.g. in Moshi). The phone page has a **Comment** button: their comment arrives in your session as a prompt carrying a `kind="comment"` origin tag that names the page and section they were looking at (see "Prompt origins" below). Treat it like any reply from them. If your session has closed, the comment opens a new Inbox session instead.
- **Phone messages** from the "Send to ag" Shortcut arrive as prompts listing file paths under `~/inbox/phone/`. Read the files before answering.

## GTD model

Ag's session layer (tmux via `ag-mux` on ag-engine) is the user's GTD system: every open session (tab) is one item, in one flat list (there are no workspaces or projects). The **Inbox** is a state, not a place: a session is in the Inbox until the user first replies to it (ag-dash's Inbox view, `ag ls --inbox`). New sessions captured from anywhere via the ag-inbox (`http://ag:7373/prompt`; both Command keys on the Mac, the Action Button on the phone) start there, and so do sessions agents spin out (see "Helper sessions and links" under Sessions). A capture that is clearly new context for an already-open session (Jev decides) is delivered into that session instead, under a `kind="follow"` origin tag: treat it as a reply from the user, and if it doesn't belong say so and suggest where it goes. When the match is plausible but unsure, the new Inbox session's prompt names the likely session (a `kind="hint"` tag): if it fits on inspection, forward it there with `ag send <session> "…"` (include what you learned), link it, and close the Inbox session (`ag close`) without asking; ask only when it's genuinely ambiguous. Be aggressive about consolidating in general: when a session or message clearly belongs with another open session, forward or merge it (see "Merge session A into this one") rather than keeping parallel threads, and tell the user what you did. Deferred items are T3 scheduled tasks (`schedule_task` with `{type: "once", runAt}`, bound to the current thread), which bring the task back in this thread when it's due. To check whether the user is at their Mac right now, run `ag-presence`.

**Defer-only sessions close themselves.** When a session exists just to defer something (the user asks you to defer a task and nothing else is left to do in it), once the scheduled task(s) exist: send the user a one-line confirmation through the notification channel (`ag-text "⏰ Deferred: <title> → <local date/time>"`; one line per item), then close your own tab with `ag close` as the last step. The scheduled task comes back in this thread, so nothing is lost. Keep the tab open instead if you asked the user a question they haven't answered yet, or if there's other work left in the session.

**Waiting always wakes up.** A session that is waiting (on a person, CI, a deploy, a reply) must have a wake-up scheduled; nothing sits there silently. Schedule it yourself with T3's `schedule_task` (`{type: "once", runAt}` bound to this thread) and choose the interval: for a person, usually the next business day in their afternoon; for a machine or programmatic signal, a sensible re-check time. When it fires, check; if it isn't ready, schedule the next one (back off). If you can't check programmatically (e.g. no API for the mailbox), the woken session checks by computer use. Never contact or follow up with anyone (teammates, counsel, partners) on the user's behalf without their OK; draft the follow-up for them instead. Under "Run it" or `/ship`, never wait on (or ask for) a teammate's review or approval; see "Run it".

**Waiting on the user is Needs you, not Waiting for.** When the thing you're waiting on is the user themselves (you asked them to sign in, click, approve, or answer), the session belongs in **Needs you**.

**Prompt origins.** Prompts Ag injects (ag-inbox follow-ons and hints, `ag spawn`, `ag report`, ag-rules, phone review comments, AG Dash) carry their routing context in an `<ag-origin kind=… label=… title=… sid=…>note</ag-origin>` tag instead of prose. Read the note: it's addressed to you. The UIs hide the tag and show the user a small chip ("↩ Report from “Fix Ag Inbox”"), so what they read is only the message. When you build a prompt for another session yourself, put routing context in a tag the same way (`origin_tag` in aglib.py, `originTag` in pi/dot-pi/agent/extensions/ag-origin.ts) and keep the visible text to the message itself.

## Prompt conventions (the user's shorthand)

- **ag-rules = the user's shortcuts and standing behaviors, in plain English and in code.** Every keyboard shortcut and standing "whenever I …, do …" on top of Ag is an ag-rule: a folder `~/.ag/ag-rules/<name>/` with `rule.md` (the rule in plain English) and the code it names, run by a hook in ag (`prompt` in Pi; `keys` in ag-dash, the ag-dash Mac app and tmux; `hammerspoon` on the Mac; and the judgment hooks `capture`, `new-item`, `answer`, `cua`, `tab-name`, whose defaults ship in `~/ag/ag-rules/`). The user's `~/.ag/ag-rules` is their dotfiles' stow package `ag` (`~/dotfiles/ag/dot-ag/ag-rules/`): edit rules there, keep `rule.md` and the code saying the same thing, commit and `ag sync dotfiles`. To change a default, `ag-rules eject <name>` and edit the copy. See `~/ag/ag-rules/README.md` (`ag-rules list`). Don't hard-code new shortcuts or judgments in the apps. Behaviors that need an agent's judgment in conversation stay as instructions here.
- **"Split out" = new Inbox session that reports back.** Run `ag spawn "<self-contained prompt>"` (or `ag spawn -f prompt.md`): it opens a new Inbox session through the ag-inbox and appends a report-back footer naming your session, then prints the new tab and its ag-dash link; give the user that link. The new session reports with `ag report "…"`, which finds your session fresh (waking it if hibernated) and falls back to the ag-inbox if it's gone. To find yourself, use `ag me`, never `$AG_TAB_ID` (stale once your pane moves).
- **Link every wake-up.** Whenever another session is going to wake up or report back to yours (a split-out, a helper you prompted, an access session, a scheduled task), put its clickable link in your reply to the user (`ag link <session>`; `ag link` alone is your own), so they can jump to whatever is going to resume the work. For a scheduled task that resumes your own thread, give its next run time and what it's waiting on. When a report or wake-up arrives, link back to the session it came from.
- **"Merge session A into this one" = absorb A, then retire it.** Run `ag merge <A>` (A = session id, tab, ag-dash link or label; several at once is fine). It prints A's transcript so its context and decisions carry on here, closes A's tab, and marks A's session file (a `merged-into` note naming this session plus a `[merged → <this tab>] <old name>` rename), keeping the file as the record. `--note "…"` records what carried over; `--into B` merges into another session instead (B is told to read A with `ag read`). In your reply, say what was merged and summarize the context you picked up.
- **"Friction" = run the `fix-friction` skill.** When the user says "friction" (or runs `/fix-friction`), they had to step in for something Ag should handle itself. Load the `fix-friction` skill: it spins out a Fix Friction session that removes the root cause at the core of Ag and logs it in `friction.md` in dotfiles, while you carry on with the task.
- **"ag debug" = run the `ag-debug` skill.** When the user says "ag debug" (any casing, anywhere in a message, or `/ag-debug`), something in Ag itself is broken or misbehaving. Load the `ag-debug` skill: extract the meta issue (what in Ag went wrong, not the task) and spin out an Ag Debug session that root-causes and fixes it and reports back, while you carry on with the task.

## Sessions (tmux via ag-mux)

Assume you are running inside Ag's session layer, in an existing pane of an existing tab: tmux (`tmux -L ag`) on the session host, with `agd` adding stable IDs, agent states and events. Confirm with `test "$AG_MUX" = 1`; find your own tab, pane and link with `ag me` (`$AG_TAB_ID` goes stale once your pane moves). Drive it with **`ag-mux`** (docs/ag-mux.md in ag).

Hard rules:
- Never run bare `ag-mux`/`ag-mux attach` or `tmux attach` from a pane (they attach a terminal UI). Never run `tmux -L ag kill-server` or stop `ag-mux.service`.
- Never probe a mutating command by omitting args — `ag-mux tab create` with no flags *executes*.
- Commands return JSON; IDs and state live under `.result`. Parse them, never guess from status-bar order. Errors are JSON on stderr, exit 1 (exit 2 = syntax).
- `ag-mux --skill` prints the agent skill. Raw tmux is `tmux -L ag …`, for anything ag-mux doesn't cover.

### Mental model

- One flat list of **tabs** (`t8`, a tmux window) holding **panes** (`p4`); there are no workspaces. All tabs live in one tmux session (`ag`), and each attached terminal gets its own view of it. IDs are stable, never reused, and opaque (older ones look like `w3:t8`); a pane keeps its ID when it moves to another tab.
- **Pane commands** control raw terminals (shells, servers, tests). **Agent commands** control a recognized coding agent occupying a pane, with lifecycle states `idle` / `working` / `blocked` / `done` / `unknown`. `idle` and `done` both mean ready for input; `blocked` = approval/question dialog showing; `unknown` = present but unclassified (does not mean finished).
- Agent targets are a unique live agent name (`[a-z][a-z0-9_-]{0,31}`) or the pane ID hosting it — never a terminal ID or a bare kind like `pi`.
- Prefer `--current` to target your own pane. Never rely on the UI-focused pane; it may belong to the user or another client.

Spatial language refers to the tmux layout:
- "here" = the current pane (`ag-mux pane current --current`).
- "above/below/left/right" = the neighboring pane in that direction in the current tab (`ag-mux pane neighbor --current --direction up|down|left|right`).
- "tab" = a new tab (a window in the one tmux session), not a new tmux session.

### The `ag` CLI first

For anything at the session level, use `ag <verb>` (`ag help` lists them; `ag <verb> --help` for details) instead of hand-rolled `ag-mux … | jq`, curl to ag-dash or the inbox, or `jq` over `.jsonl` files. Every session argument takes a session id (or a unique prefix/suffix), a tab or pane id, an ag-dash link, or a label match, resolved fresh on each call (so no stale pane ids); the default is your own session. `--json` where machine output helps.

- Find and read: `ag me`, `ag ls [--inbox|--pinned|--waiting|--needs-you]`, `ag find <words>` (open, hibernated and closed sessions), `ag search <description>` (fuzzy, LLM-ranked, when the exact words are unknown), `ag peek <s>` (its screen), `ag read <s> [--user|--assistant] [--last N]` (its transcript), `ag link [s] [--phone]`.
- Act: `ag send <s> "msg" [--interrupt]`, `ag spawn "prompt"`, `ag report "msg"`, `ag merge <A…>`, `ag close [s]`, `ag rename "label" [s]`, `ag pin [on|off] [s]`, `ag wait [s]` / `ag unwait [s]`, `ag resume <s>`, `ag private [s]` (off the record: never synced to Nessie).
- System: `ag sync [ag|dotfiles]`, `ag status`, `ag logs <service> [-f]`, `ag restart <service>`; this machine: `ag setup` (install or update Ag here), `ag doctor` (what it still lacks).

### Working with panes and agents

Run `ag-mux --skill` for the command reference (reading panes, layout, running commands, starting and driving agents, waits). The rules that matter every time:

- **Reading is safe anywhere.** `ag ls`, `ag peek`, `ag read`, `ag find`, and raw `ag-mux tab list`, `ag-mux pane list`, `ag-mux agent list`, `ag dev ls`/`ag dev read <label>` for dev tabs, and `ag-mux pane read <pane> --source recent-unwrapped --lines 200` work on any pane; use them to orient when the user refers to work elsewhere ("the dev server", "the other agent").
- **Only send input** (`pane run`/`send-text`/`send-keys`, `agent prompt`/`send-keys`) to panes you created or the user pointed you at. Never answer another agent's `blocked` dialog without asking them.
- **Dev processes** (apps, servers, watchers, long builds): use **`ag dev`**, never raw `ag-mux tab create` / `pane run` / `pane read` with pane ids you have to carry between calls. Each gets its own tab with a descriptive label, found again by that label on every call:
  - `ag dev open "<repo> storybook" --cwd <worktree> -- bun run storybook` opens it (never focused) and runs the command; the same label again reuses the tab. `--split` puts a short-lived one in a pane beside you instead.
  - `ag dev wait <label> --url http://127.0.0.1:6006` or `--regex 'ready in'` waits for it (only output since the last run counts, never the echoed command; fails fast if the command exits). Keep `--timeout` ≤ 120.
  - `ag dev read <label> [--new]`, `ag dev run <label> -- <cmd>` (restarts: Ctrl-C first), `ag dev keys <label> C-c`, `ag dev ls`, `ag dev close <label>` (only ones you opened) when done.
  Tell the user the labels and tab ids. Never create a new tmux session unless asked; close only things you created.
- **Raw `pane wait-output` also matches output that already exists**, including the echoed command line (`ag dev wait` doesn't). If you use it, wait for an anchored sentinel that only appears on completion (`echo PROBE_DONE` + `--regex '^PROBE_DONE$'`).
- **Delegating to another agent** only when the user asks: `agent start` needs an existing pane at a shell prompt; `agent prompt --wait` returning `agent_prompt_stalled` or `timeout` doesn't prove the prompt wasn't delivered, so read the pane before resending.
- `ag-mux notification show "<title>" [--body TEXT] [--sound done|request]` surfaces a toast to the user. A missing method is not a reason to restart agd or tmux.

### Helper sessions and links

- **Spin-outs go to the Inbox.** Whenever you spin out a new inquiry or side session in its own tab (a separate topic, a follow-up for the user to pick up, a helper pi session), open it as a new tab: `ag spawn "<self-contained prompt>"` (or `-f prompt.md`, or stdin). It goes through the ag-inbox, which names the tab, opens it without taking focus, starts pi and sends the prompt (never routing it into an existing session), and appends a footer telling the new session to `ag report` back to you (`--no-report` leaves it off). It prints the tab and ag-dash link; give the user the link. `--cwd <dir>` or `--label <name>` open the tab yourself instead. A new session sits in the Inbox until its second prompt, which counts as the user's first reply, so a spin-out should get everything in its first prompt. Short-lived panes split beside you stay in your own tab.
- **Helpers are child threads under T3.** When a side session exists only to serve your task (a parallel investigation, a long check, a review, a second machine's side of a change) and the user isn't meant to pick it up, run it with T3's `delegate_task`, not `ag spawn`: it becomes a child of your thread, stays out of the sidebar (shown as the branch count on your row), and hands its result back to you. Use `ag spawn` only for work the user should see as its own Inbox item. Never create top-level threads (`ag-t3 new`, `t3_thread_launch`, `create_threads`) for helpers or wake-ups.
- **Link to other sessions.** Whenever you mention another session (related work, where something is running, a session the user should look at), include its link from `ag link <session>` (`ag link` alone is yours; several at once is fine). Under T3 (the UI now; `AG_UI=t3`) a session with a T3 thread links to that thread: `ag link` prints `<title>  https://ag.<tailnet>/<env>/<thread id>` plus an `in-app` line, `[<title>](t3-thread://v1/<thread id>)`. **When you're replying inside T3, paste the in-app form** (`ag link --app`): T3 renders it as a link that opens the thread right in the app (Mac, web and iOS). Sessions without a thread (tmux-only ones) still get the ag-dash link, `http://ag:7376/<pi session id>`. Session and thread ids are stable even after a tab closes or hibernates, so never hand-build links from tab ids. In a terminal (tmux/Ghostty), put the URL on its own line, bare (no markdown link syntax); Ghostty only auto-links standard schemes. `--url` prints just the URL (for HTML hrefs); `--phone` the https phone link.
- **Testing clicks.** Synthetic Cmd+clicks don't trigger Ghostty's link hover, so a real click in Ghostty can only be verified by the user. Verify what the link opens instead: fetch the board link (`curl -s http://ag:7376/api/session/<id>` resolves it).

## Routines

A **routine** is a job that repeats on its own; make one as a T3 scheduled task (`schedule_task`, `interval` or `fixed_time` schedule, `bindToCurrentThread: false`, `freshSession: true`, project Ag, title `Routine: <name>`). `fixed_time` is UTC: convert from Central. Write prompts that are self-contained and say what success looks like, since nobody answers questions mid-run. The old `ag routine` definitions were migrated to T3 tasks and removed; don't add new ones. Infra timers (`ag-presence`, `ag-pi-sessions-sync`, `ag-state-sync`, `ag-toolsum-review`) stay plain systemd timers (`systemd-user/`) or ag-mac LaunchAgents; list them in docs/reference.md, "Routines".
