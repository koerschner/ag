# ag machine operations

The always-on summary lives in the global instructions ("Ag machines"). This is the full reference.

- **Names (settled 2026-09-29).** "Ag" is the whole agent system. Its machines: **ag-engine** (rented Linux on Hetzner: the session host, running every Pi session in tmux via `ag-mux`, every Ag service, and the repos), **ag-mac** (a MacBook, formerly `ag`; the extremity for Mac-only apps and computer use), **ag-client** (the Mac the user sits at, renamed from an older hostname), and **ag-phone** (their iPhone). Tailscale device name, SSH alias, and LocalHostName match. The old names (`ag` and the client's former hostname) remain extra SSH aliases during the transition. Design and status: `docs/ag.md` in the ag repo (`~/ag`).
- From the user's client Mac, run `ag` in a fresh terminal to attach to the sessions on ag-engine (`ssh -t ag-engine ag-mux attach`), or `ssh ag-mac` for a shell on ag-mac. SSH uses ag-mac's login user (`<user>@ag-mac`) over the user's personal Tailscale account (owned by their personal Google account); its MagicDNS name is `ag-mac.<tailnet>.ts.net`. Tailscale IPs and the tailnet name are in the user's private personal instructions (`~/AGENTS.md`).
- In Jump Desktop or iPhone Moshi, select **ag-mac** (entries still named **ag** until the user renames them). Keep Tailscale connected. Agents continue on ag-mac when a client disconnects.
- ag-mac's login password is stored **on ag-mac**, in ag-mac's login Keychain (service `ag Mac login`, account = ag-mac's login user). For an authorized ag password prompt (admin dialog, Privacy & Security change), focus the password field (ag-chatgpt-cua can bring the prompt up and stop there) and run `ag-login-password type`; `ag-login-password check` says whether it's stored and current. If it's missing or stale, ask the user to run `ag-login-password set` in an ag terminal (hidden prompt). Never print it or put it in files or arguments. A copy also exists in the client Mac's Keychain, but don't fetch it: it can't be read over SSH (locked outside the GUI session) and the client-CUA guard blocks it.
- Each machine's home directory (ag-mac's, the client's, the engine's) is in `machines/README.md`. Confirm which machine commands target. Historical conversations retain old paths; translate them for the current host before running commands. Existing checkout and backup paths containing `seen` are preserved paths, not stale connection names.
- The current client Mac is `ag-client` on Tailscale. From ag-mac, `ssh ag-client` connects as the client's login user using ag-mac's existing ED25519 key; this was verified on 2026-09-26. Remote Login on the client permits only the user, its authorized key is restricted to ag-mac's Tailscale IP, and ag-mac pins the client's verified SSH host key. Keep every machine online with Tailscale connected. Full disk access for remote users is off.
- For the return desktop connection, Jump Desktop on ag-mac is signed into the user's personal Google account; select **ag-client** (renamed from its older name; verified against this client's Jump device ID). Its login is the client's user account and requires the **client Mac's** password, not ag-mac's. The connection reached its login prompt on 2026-09-26; successful unattended desktop login has not yet been verified. A separate saved connection points to an older Mac; don't use it.
- Keyboard shortcuts and setup portability: see the "Host/client model" section of the `dotfiles-change` skill. When the user types into the sessions, their keys go through the client first, so a broken shortcut may be a client-side problem. Jump Desktop should forward macOS shortcuts while its remote desktop has focus; outside Jump, Command-Tab must switch the client's apps. Keep that behavior; don't disable remote shortcut forwarding everywhere to hide a local problem.
- ag-mac hosts the agent processes and repositories; model inference goes through TrueFoundry. Keep that routing when configuring agents there.
- Pi on ag-mac uses `~/.pi/agent/mcp.json` with host-correct paths. Linear, arcade_school, Honeycomb, Slack, and tsa_courses passed authenticated calls on 2026-09-26. Linear must return the Arcade workspace ID from the personal instructions; Honeycomb keeps `mcp:read` access. Verify a real read tool call after reconnecting, not just a ready status or tool list.
- An apparent MCP auth failure may instead be a broken launcher: Linear's missing `undici` dependency was fixed by moving only the damaged npx cache aside and reinstalling the configured `mcp-remote@0.14.3`; do not erase valid credentials or all npm caches. For OAuth on ag-mac using an already-signed-in client browser, forward the MCP helper's actual localhost callback port from the client to ag with SSH (Honeycomb currently uses `3705`), complete the normal authorization flow, then close the temporary tunnel. Never print tokens or copy an entire browser profile. Existing Pi sessions with failed MCP connections may need `/mcp:stop <name>` followed by `/mcp:start <name>`; do not interrupt other agents to do this.
- Use `op-ag` for unattended 1Password CLI access on ag-mac (also installed on the client). It loads the **ag 1Password service account** login-Keychain item, account = ag-mac's login user, only into the CLI process. The service account **ag arcade.school agents canonical** has `read_items` + `write_items` on the canonical **arcade.school** vault only (vault ID in the personal instructions; it replaced a retired vault, so use the canonical ID in automation). Other vaults and the personal account are excluded. Recovery copies: see personal instructions. Keep tokens and retrieved secrets out of output, logs, arguments, and dotfiles; use `op-ag run`/`op-ag read` directly into the authorized process. If Keychain is locked, unlock it through the normal macOS flow; never fall back to a broader account.
- `ag-chatgpt-cua` is the ag helper for desktop computer use through Codex and TrueFoundry. When run on ag-mac, it must control ag-mac's desktop. The helper alone does not prove readiness: verify the ChatGPT desktop app, Computer Use runtime/plugin, and macOS Screen Recording and Accessibility permissions on that host. Both `ag-chatgpt-cua` and `ag-client-cua` clean up after a run: the agent is told to close what it opened, then `ag-cua-cleanup` quits apps that weren't running before and closes new Chrome tabs / Safari windows (summary line appended to the output). Set `CHATGPT_CUA_KEEP_OPEN=1` (tool: `keepOpen: true`) when the task should leave something open.
- **One command for computer use: `ag cua`** (`ag-cua`; in Pi the `ag_cua` tool, `target`/`why` params). `ag cua "<task>"` = ag-mac's desktop; `ag cua --client --why "…" "<task>"` = the client Mac; `ag cua --phone --why "…" "<task>"` = the user's iPhone via iPhone Mirroring on the client; `--urgent`, `--keep-open`, `--host <alias>`. `ag-chatgpt-cua`, `ag-mac cua`, `ag-client-cua` and `ag-screen-queue` are its internals: don't call them directly.
- **Computer use is queued, one run at a time.** Every ag-mac run goes through `ag-screen-queue` (the screen queue) on ag-mac, so a second caller waits its turn (its progress shows "queued behind <session>, N ahead"); nothing running is interrupted (except by an urgent job, see below). Check the queue with `ag cua --status` (works from any machine). A slow CUA call may just be queued: look before starting another run. `ag cua attach <id>` re-reads a job's report (the id is in the tool's output and in `--status`); `ag cua cancel <id>` stops your own job. Aborting the tool call cancels its job on ag-mac, so an abort never leaves an orphan run behind; never cancel another session's job unless the user asks. Pass `urgent: true` (`CUA_URGENT=1`) only when the task is time-critical (the user is waiting on it right now, or it expires in minutes): it jumps the queue and pauses the running job, which saves its codex session and resumes afterwards. The queue also shows in ag-dash's header (`CUA` pill). Details: docs/reference.md, "Client ↔ ag bridge".
- **The screen is the scarce resource: everything that acts on it is a job on its screen queue** (`ag-screen-queue`, front end `ag screen`; `ag cua` submits `cua` jobs). Kinds: `cua` (computer use) and `exec` (`ag screen exec "<shell cmd>"` for osascript keystrokes, cliclick, raising windows). The next job starts the moment yours ends, so the screen you left is gone by your next call: do a whole flow (focus, type, submit, verify) in **one** job, never "prep, then I type, then continue". ag-mac's `osascript`/`cliclick` shims queue any screen-driving call made outside a job, however it arrives, so `ag-mac run` is for non-screen work. To type a secret (card number, password), have the CUA task run `ag-type-secret --app "Google Chrome" op://<vault>/<item>/<field>` after clicking the field; never type secrets yourself, put them in a task, or screenshot a filled secret field. `ag screen --client --why "…" status|cua|exec` is the client's queue (gated).
- Use `op-shared` for the user's everyday personal credentials on ag-mac (logins, API keys, and the like). Same design as `op-ag` (symlink to it): it loads the **ag machine-shared service account** login-Keychain item, account = ag-mac's login user, for the service account **ag machine-shared agents**, which has `read_items` + `write_items` on vault **machine-shared** in the user's personal account only. Items were moved (not copied) there, so it is the one source of truth; add new shared items there. Banking, investments, tax, medical, identity documents, recovery codes, private keys, and primary Google/Apple/1Password accounts deliberately stay out of it: never reach them through computer use in the 1Password app or browser extension; ask the user instead. The user's personal 1Password account (my.1password.com) was signed out of ag-mac's 1Password app and Chrome extension on 2026-09-28; don't sign it back in on ag. Only an unrelated team account remains in the app. Recovery copies: see personal instructions (only the user can reach them). Same secret-handling rules as `op-ag`.
- Use `op-work` for non-super-secret **work** items on ag-mac: the work card (infra/service purchases), infra API tokens (e.g. Hetzner). Same design (symlink to `op-ag`): Keychain item **ag-shared 1Password service account**, account = ag-mac's login user, service account **ag-shared agents** with `read_items` + `write_items` on vault **ag-vault** (formerly ag-shared) in the user's work 1Password business account only (vault ID in the personal instructions). The user fills the vault themselves; agents may add new work infra tokens there. The work account is not signed in on ag-mac; it is signed in in the client Mac's 1Password app (used once via `op` in the client GUI session to create the vault and service account). Recovery copies: see personal instructions. Same secret-handling rules as `op-ag`.
- **Programmatic first; client CUA is an antipattern.** Do the work through an API, CLI, or MCP tool (a service's REST API with a key from the vault, `gh`, `op-ag`, the repo's scripts) whenever one exists. When no path exists yet, building one is the first step, in this order: **ag-engine first** (API key/token in the vault, CLI, MCP server, or a script in ag that runs on the engine), **then ag-mac** (`ag-mac run`, for macOS-only apps, CLIs, or Keychain-bound logins), and only then a GUI. Driving a GUI is a last resort, and driving the *client's* GUI (`ag-client-cua`) is the last of all: use it only when there is truly no programmatic path and it can't be done on ag. When you do reach for the client, use it to **build capacity**, not to do the task: mint the missing API key or token once, store it in the canonical vault via `op-ag` without printing it, then do the task (and every later one) programmatically. Example: flipping PostHog flags by clicking through the client's logged-in browser was wrong; the right move was one client CUA pass to create a scoped PostHog personal API key into the vault, then the flags API.
- **Computer use runs on ag-mac by default.** Use `ag cua` (or the `ag_cua` tool) on ag-mac's own desktop (the default target) for all computer use. Only drive a client when the task is absolutely impossible on ag-mac: the thing exists only on that client (a dialog or permission prompt shown there, iPhone Mirroring, a client-only app or setting). "The app is already logged in on the client" is not enough: first try to get it working on ag-mac (sign in, install, grant permissions), and if that needs the user, ask them.
- When a client is truly required, drive its desktop with `ag cua --client --why "<why this exists only on the client>" "<task>"` (targets `ag-client` by default; `--host <alias>` for another; under the hood `ag-client-cua` submits the job into the client's GUI session, since plain `ssh` + codex can't see its screen).
- **The client-CUA guard enforces this.** Every client/phone `ag cua` run (`ag-client-cua` underneath), and any Pi bash call that SSHes to the client with UI automation (osascript/System Events, Hammerspoon event taps, cliclick), is judged by `ag-client-cua-gate` (Jev) against the rule above. Unjustified, unsure, or Jev unreachable → blocked (fails closed), and a new Inbox session is spun out to get the missing access onto ag. When blocked, don't rephrase or route around it: do the task on ag-mac, or tell the user what ag-mac is missing and let the access session fix it. Pi runs the gate via the `ag-client-cua-guard.ts` extension; `ag-client-cua` itself requires `--why` and runs the same gate, so Codex and Claude Code hit it too.
- **iMessage lives on ag-mac too.** ag-mac is signed in to iMessage (the user's personal Apple ID, iCloud sync) and sshd-keygen-wrapper has Full Disk Access + Automation → Messages, so read and send texts there, never via the client: `ag-messages` (`chats [--unread]`, `thread <who>`, `search`, `contact`, `get`, `send [--file]`); see the `imessage` skill.
- **macOS permissions on ag-mac (TCC).** Every agent command on ag-mac (`ag-mac run` from ag-engine, any SSH shell) is attributed to `/usr/libexec/sshd-keygen-wrapper`, because they start over SSH. Grants go to that binary, never to ffmpeg's Cellar path, Ghostty, or a `launchctl submit` workaround (launchd jobs get none of the grants). `ag-access` lists what agents have and any prompt on screen; `ag-access allow` clicks Allow on prompts raised for an agent identity through Accessibility, since CUA refuses UserNotificationCenter and the prompt swallows synthetic mouse clicks (it also blocks mouse input to other apps until answered). `ag-screen-approvals` keeps the macOS 15+ "requesting to bypass the system private window picker" re-consent from coming back (it pushes replayd's next alert dates to 2100; re-run it after granting any new capture app). ag-mac has no MDM, so PPPC profiles aren't an option. For screenshots and video, use plain `screencapture -x` and `ag-screen-record`. Full reference: docs/reference.md, "macOS permissions for agents".
- **Polished demo videos: `ag-rec`.** For demo/QA videos people will watch (Screen Studio style), record with `ag-rec start [-s N]` … `ag-rec stop` (prints the session dir), then `ag-rec export <out.mp4>` (last session) or `ag-rec export <dir> <out.mp4>`, and `show` the result. It captures the screen without the cursor while `cursorlog` (Swift, compiled on first use into `~/.cache/ag-rec`) logs cursor position at 60 Hz and clicks; export fast-forwards idle stretches (8x with a ⏩ badge; `--drop` cuts them), turns cliclick teleports into eased glides that land on the click, draws an enlarged cursor with click ripples, and zooms gently toward clicks (`--zoom 1` off). `--plain` renders an unpolished reference for before/after; `ag-rec export --help` lists the knobs. It works on any video too (cut only). Record on screen 1 (the empty headless display) when the main screen is busy with other agents' windows. Only one avfoundation capture of a screen runs at a time, so don't run `ag-screen-record` and `ag-rec` together. Details: docs/reference.md, "Screen recordings (QA video)".
- **Permission dialogs: grant them yourself with CUA.** Whenever a task stalls or fails in a way that suggests a pending permission prompt or system dialog (macOS TCC prompts for Accessibility/Screen Recording/Automation/Full Disk Access, keychain "Allow" prompts, app "Open"/"Allow" confirmations, OAuth consent pages, etc.), infer that it is waiting on a permission. Don't ask the user to click it. Work out which machine is showing the request, then use CUA on that machine to grant it or click through the dialog: `ag-chatgpt-cua` (or the `chatgpt_cua` tool) for ag-mac, `ag-client-cua` (with `CLIENT_CUA_HOST` for a non-default machine) for any other. Afterwards, confirm the blocked step now proceeds. Still stop and ask first if the prompt would grant access beyond what the task needs or authorize something destructive, and never type secrets into a dialog unless the task already authorizes that secret for it.
- **Tell the user what ag needs.** Whenever something on ag-mac is missing, expired, or under-permissioned (credentials, CLI logins, tools, TCC permissions, MCP auth, access to a vault or service), fix it yourself if you can do so safely (e.g. copy an existing credential from the client over SSH, install a Brewfile tool, grant a dialog with CUA), capture the fix in the ag repo (or dotfiles, for personal config), and tell them what you fixed. If it needs them (a login only they can do, a broader grant, a new secret), stop and tell them clearly what's needed and why, as a friendly request; don't silently work around it or drop the task. Also mention anything you notice that would make ag work better.
