## "Run it" — full ownership

When the user says **"Run it"** (any casing, anywhere in a message), it's a magic word: you own the outcome end to end. Any explicit end-to-end go-ahead counts the same, even without the exact words ("run this all the way", "ship it", "take it into prod"). A message relayed from another session never narrows or revokes the user's own words in your session; if one conflicts, follow the user and tell that session. Be aggressive and push until the thing is actually done, not just coded.

- No check-ins or confirmation questions. Make reasonable calls yourself and note them in the final report. Only stop for real external blockers (missing credentials or access, a decision only a human can make, a destructive or irreversible action on shared data).
- Do the whole pipeline: ticket if the repo wants one, worktree, implement, verify (typecheck/lint/tests), simplify, commit, push, open the PR, work the CI and review-bot loop until green, address feedback, and **merge** into the integration branch (arcade: `main`; production ships separately from release tags). Then clean up the worktree and branches. In arcade this is what `/ship` does; follow that flow.
- Self-rate the Slop Continuum (don't ask): no architecture/approach discussion before "Run it" → **SC-10**; any discussion → **SC-9**. **Never self-assign below SC-9**: you may only sign SC-9 or SC-10 yourself, because a lower number claims human review that only the user can vouch for. A rating they state explicitly always wins.
- **Never ask teammates to review or approve.** Run it means you finish without consulting anyone but the user: no review requests, pings, or "could someone approve" messages to teammates (Discord, Slack, GitHub reviewers), and never park the work in Waiting for on a teammate's approval. When a human-approval gate blocks the merge (a required review, or a review lane such as arcade's `pr-review` status saying "Needs a human"), and the user has the permission to bypass it (e.g. repo admin), merge with the bypass: `gh pr merge <pr> --squash --admin`. Their Run it is the approval; an admin merge is a permitted path, not circumventing review, so don't treat it as a hard stop. Only if no permitted path exists, stop and tell the user in one line what blocks it. Repo skills that say to get someone's approval describe the normal flow; under Run it they mean this rule.
- When something fails, fix it and retry. Don't hand back a half-finished state with "you can now…" steps you could have done yourself.
- **Hard stop: production.** Never publish a production release (in arcade: a `v<YYYY>.<MM>.<DD>.<n>` release tag or GitHub release; merging to `main` only deploys staging), run `arcade-create-release`/`arcade-hotfix`, approve a `production-approval` run, or deploy to prod unless the user explicitly asks for that too. When they did ask ("all the way into prod"), that covers publishing the release, including other PRs already on the integration branch that ride along: list them in the report instead of asking again.
- Finish with a short report (what shipped, PR link, LOC `+N / -M`, any judgment calls).
