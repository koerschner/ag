# T3 Code as Ag's UI

Status: **migrating** (started 2026-10-07). [T3 Code](https://github.com/pingdotgg/t3code) (MIT) replaces
ag-dash and the tmux tabs as the place sessions live: desktop app, web, and iOS, all on one server.
Everything else in Ag stays: the ag-inbox and its capture paths, routines, `ag-mac`, computer
use, secrets, MCP.

## How it fits

| Piece | Where |
|---|---|
| Server | Upstream `pingdotgg/t3code` (nightly). `ag-t3.service` runs `~/.local/bin/t3 serve` on `127.0.0.1:3773`, which execs `~/.t3/runtime/versions/<version>/t3` (layout from `https://t3.codes/install.sh`). Data lives in `~/.t3` (`-> /data/t3`). Published at `https://ag.<tailnet>.ts.net` (port 443 on `svc:ag` via `ag-svc`). `ag-t3-update` updates it (see "Updating and rolling back"). Until 2026-11-15 it ran Nathan's fork `koerschner/t3code` (now retired, see its `FORK.md`). |
| Mac app | Upstream T3 Code (Nightly) on the client Mac and `ag-mac`, installed from the GitHub release DMG (`T3-Code-<version>-arm64.dmg`). Self-updating. Uses bundle ID `com.t3tools.t3code` and profile `t3code-v2`, so connections and drafts carry over from the retired `T3 Code (Ag)` (now in `/Applications/Retired/`). The ag-mac copy is paired to the same server so agents test the Mac app on ag-mac's screen, never the client's. |
| Phone | Upstream's iOS app (TestFlight), paired with the server. |
| Agent | Pi, with the real `~/.pi/agent` (AGENTS.md, skills, extensions, models). ag's tmux-only extensions switch themselves off without `AG_MUX=1`. A T3 thread *is* a Pi session file. |
| Links | `ag link` (and every `ag` verb that prints a link, `ag me`, `ag ls`, `ag spawn`, the spawn/report footers) gives a session its T3 thread's URL `https://ag.<tailnet>/<environment id>/<thread id>` when `AG_UI=t3` and the session has a thread (looked up in T3's sqlite by Pi file; ag-dash's `http://ag:7376/<sid>` otherwise). `ag link --app` prints `[title](t3-thread://v1/<thread id>)`, which T3 renders as a link that opens the thread in the app; agents paste that form when replying inside T3. Every `ag` verb also accepts a thread id or T3 URL as the session reference. |
| Bridge | `ag-t3` (bin): `new`, `send`, `thread`, `threads`, `import`, `refresh`, `link`, `delete`, `setup`, `doctor`. Talks to T3's WebSocket RPC (`orchestration.dispatchCommand`) with an admin token in `~/.config/ag/t3.token`. |
| Mode switch | `AG_UI=t3` in `~/ag-personal/env`. Then the ag-inbox makes captures T3 threads (Jev's follow-on matching runs over T3 threads), `ag send`/`ag report` (aglib `prompt`) queue into the session's T3 thread. Restart `ag-inbox.service` after changing it. |

## Updating and rolling back

- **Server updates:** The `t3-update` T3 scheduled task runs `ag-t3-update` daily at 4:07 AM Central to match the Mac and iOS nightlies.
- **`ag-t3-update` behavior:** Installs the newest npm `nightly` dist-tag (or `--version V`) and keeps the 3 newest runtimes. It waits up to 3 hours for running turns to finish because a restart cancels them (`--now` skips the wait). It rewrites `~/.local/bin/t3`, restarts `ag-t3.service`, checks `/.well-known/t3/environment`, and rolls back the launcher if unhealthy within 2 minutes. `--backup` stops the server first to copy `statev2.sqlite*` to `~/.t3/backups/` and restores it on failure. `--status` shows the running version and recent runs from `~/.t3/ag-t3-update.jsonl`.
- **Do not use upstream updaters:** Never run `t3 update` or `t3 service install`. `ag-t3.service` is Ag's own unit with a `zsh -l` environment and model keys.
- **Mac keychain:** On first launch, macOS asks for the `t3code Safe Storage` keychain item because the upstream app is signed differently than the ad-hoc fork build. Click Always Allow using that Mac's login password. Never delete this keychain item. It encrypts `~/.t3/userdata/connection-catalog.json` on the Mac, and losing it requires re-pairing.
- **30-day pairing:** Paired logins expire after 30 days (upstream default, down from 365 in the fork). Re-pair monthly with `ag-t3-pair-client`.
- **Rolling back to the fork:** Use only if upstream breaks. Fork builds remain in `~/.local/share/t3-builds` (current is `2c91a408ea`), and the repo `koerschner/t3code` stays on GitHub (marked retired in `FORK.md`). The switch on 2026-11-15 took no database backup and upstream migrated the database to schema 95, which the fork can't read, so a return needs a backup from `ag-t3-update --backup` taken before that date's fork could run, or a fork rebuilt on current upstream. With such a backup: stop `ag-t3.service`, restore its `statev2.sqlite*` from `~/.t3/backups/`, run `AG_T3_FORK=1 ~/t3code/ag/ship --rollback` (fork scripts require `AG_T3_FORK=1`) or point the launcher at the fork build, and start `ag-t3.service`.

## Re-pairing a Mac app (expired login)

When T3 Code (Ag) on the client Mac (or ag-mac) loses its server login (`ag-t3.service` logs "Session token
expired"), re-pair it from the session host with **`ag-t3-pair-client [client|mac]`**; never drive the
client's screen for it. It mints a one-time 20-minute credential into a private temp file, opens the app's
`t3code://pair?pairingUrl=…` link on that Mac through `ag-client run` / `ag-mac run` (the link goes over
stdin, never into arguments or output), and waits for it to be used. The app asks "Add the backend at
https://ag.<tailnet>.ts.net?": that one click is the only step on the Mac (Nathan's, or a client CUA run
justified as a dialog showing on the client). Re-pairing updates the saved connection in place (same
environment id and origin), so chats, projects, settings and drafts stay. An unused credential is revoked
when the wait ends (`--wait SECONDS`, default 300). Paired sessions last 30 days, so expect this about monthly.

## Pairing a replacement iPhone

Connect the phone to the same Tailscale network, then open T3's Settings → Environments → Add environment.
From the Mac running Mirroring, capture a fresh one-time credential from the session host into a private
temporary file, then copy only the credential to that Mac's clipboard through the authorized screen workflow:

```sh
pairing_file=$(mktemp -t t3-phone-pairing)
chmod 600 "$pairing_file"
printf 'Pairing file path: %s\n' "$pairing_file"
ssh ag-engine 't3 auth pairing create --label "phone T3" --ttl 20m --json' > "$pairing_file"
jq -rj '.credential' "$pairing_file" | pbcopy
```

Record the printed path (it is not a secret), so cleanup works even in a later shell. Never print the JSON
or credential into a tool result. Paste the clipboard into the phone's **Code** field.
Enter **`ag.<tailnet>.ts.net` without `https://`** in Address and the credential in Code. The native iOS
build tested during replacement-phone setup rejected a scheme-prefixed address with “Pairing URL is
invalid”; the bare hostname paired successfully over HTTPS. T3 Connect sign-in is not needed.

For iPhone Mirroring, enter the fields manually; the phone camera is unavailable from the Mac. If simulated
keystrokes drop characters, use the phone's text-editing **Paste** menu and verify the address. Keep the
credential out of chat, screenshots, and autosaving editors. Verify **ag-engine · Connected**, open an
existing conversation. If pairing fails or is abandoned, read the non-secret `id` from the private JSON
and run `t3 auth pairing revoke <id>` on the session host before deleting the file. `t3 auth pairing list`
can also find an unconsumed credential without revealing its secret. Whatever the result, remove the file
at the recorded path and clear the transfer clipboard (`printf '' | pbcopy`). Do not rely on shell
variables surviving between separate tool calls.

## Migrating sessions

`ag-t3 import --all-open` turns every open ag session into a T3 thread:

- `thread.create` with `importedNativeThread {driver: pi, nativeId: <session file>}` binds the thread to the
  existing Pi session, so the next message resumes it natively (full context, tools and all).
- T3 doesn't read a Pi file's history into its view, so the active branch's user turns and assistant replies are
  written as v1 transcript rows (`projection_thread_messages` + `orchestration_v2_legacy_imports`); T3's v1
  importer hydrates them the first time the thread is opened. `ag-t3 refresh` re-snapshots threads not yet opened.
- Title, pin (and pin order) carry over. Inbox / Needs you have no T3 equivalent yet (T3 refuses mark-unread on a
  thread without a run).

Never let a session run in both places: once a session is in T3, close its tmux tab (or let it finish first). `ag-t3 import` skips a Pi file still held by a live or sleeping tmux tab. Closed sessions can be imported from their Pi file path.

## Model selection safety

T3 has two Pi lanes, both on the same **TrueFoundry** models; they differ only in where Pi stores the session. A thread's first message decides which one it runs in ("Off the record" below): only FreeTime work syncs.

- **`pi`** ("Pi · work", the default instance): synced. Sessions under `~/.pi`, which Nessie syncs.
- **`piPrivate`** ("Pi · private (unsynced)"): off the record. Same Pi, config, extensions and models, but the instance sets `PI_CODING_AGENT_SESSION_DIR=~/private-chat/pi-sessions` (T3 never passes a session dir, so the environment decides; `ag-pi-private` uses the same folder), so Nessie never sees its sessions.

Work Claude runs on TrueFoundry like every other work model, so work needs no instance of its own. Personal Claude runs on Nathan's own Claude plan, in Pi ("Pi · personal", "Personal Pi lane" below) or in T3's own Claude Code ("Claude · personal", "Personal Claude" below).

T3 shows Pi's entire model catalog (about 515 models: hundreds of personal OpenRouter models and the direct `anthropic` and `openai-codex` logins next to the TrueFoundry ones) for every Pi instance, so a composer can default to a model outside TrueFoundry. On 2026-10-11 new `pi` threads picked `anthropic/claude-opus-5-5` (whose OAuth refresh failed) and `openai-codex/gpt-6-astra`, and a T3 client kept writing such selections back. Three layers keep every Pi thread outside the personal lane on TrueFoundry:

- **Server-side model preferences.** Since upstream #16816, T3 keeps favorites, hidden models and model order in server settings and syncs them to every client (`favorites`, `providerModelPreferences.<instance>.{hiddenModels,modelOrder}` in `~/.t3/userdata/settings.json`). `ag-t3 setup` hides every model outside TrueFoundry in both lanes' pickers (the private lane's mirrors the synced lane's), puts TrueFoundry Opus first and favorites it. New models from catalog updates stay visible until setup runs again; `doctor` warns about them.
- **Pi's extensions.** In every session outside the personal lane (either lane, tmux sessions, routines), `truefoundry-only` switches a pick outside TrueFoundry (the direct `anthropic` and `openai-codex` logins, OpenRouter) to the TrueFoundry copy of the same model (`anthropic/claude-opus-5-5` and OpenRouter's `anthropic/claude-opus-5.5` → `truefoundry/anthropic-primary/claude-opus-5-5`, `openai-codex/gpt-6-astra` → `truefoundry-openai/gpt-6-astra`), else to TrueFoundry Opus. T3 doesn't reflect the switch in its composer, which is why hiding comes first.
- **Thread selections.** `ag-t3 doctor` flags threads whose saved model is outside TrueFoundry; fix them with `t3_thread_configure` (or the composer) using the TrueFoundry copy, e.g. `truefoundry-chat/fireworks-group/glm-5p3` for GLM. Don't change the model of a thread that is mid-run (see below).

**Moving a thread between lanes.** `ag-t3 send --instance piPrivate --model truefoundry/anthropic-primary/claude-opus-5-5 [--thinking max] <thread> <text>` queues a message that carries the new selection. T3 plans the switch when that message's run starts, after any active run (`t3_thread_configure` to another instance on a running thread detaches its live session at once, cutting the turn off). It starts a new native Pi session in the target lane with T3's context handoff: a digest of the thread capped at about 16,000 tokens (`T3CODE_CONTEXT_HANDOFF_TOKEN_CAP`); the full history stays readable with `t3_thread_read`. The earlier transcript stays where it was (already synced, if it began in the `pi` lane). A model change within a lane keeps the same Pi session.

**Off the record.** The server no longer checks `ag-rules` lane rules before each message, so saying "off the record" does not move a thread to the private lane automatically. Threads start in the synced lane (`pi`) in the Work project. Move the thread yourself before sending private text: run `ag private [session]`, pick a model under "Pi · private (unsynced)" in the composer, or run `ag-t3 send --instance piPrivate --model <model> <thread> <text>`. Lane switch behavior is otherwise unchanged: T3 hands over a digest capped at ~16k tokens, queued behind any running turn. Personal Pi and Personal Claude lanes are unchanged.

**Work and Personal projects.** The project picker picks the lane, both over the home directory: **Work** (`~`, formerly "Ag") starts threads on TrueFoundry Opus in `pi`, and **Personal** starts them on `claude-bridge/claude-opus-5-5` in `piPersonal` (each project's `defaultModelSelection`). T3 allows one project per path and doesn't resolve symlinks, so Personal's root is `~/.t3/roots/personal`, a symlink to `~`; processes resolve it, so Pi and the shell see `/home/nathan` as cwd and load each AGENTS.md once. `ag-t3 setup` keeps both (symlink, titles, defaults). A thread keeps the lane it starts in; the model picker can still switch it (a lane switch hands over a digest, and personal → work puts that digest in the synced lane).

**Personal Pi lane.** `piPersonal` ("Pi · personal") is Pi on Nathan's personal Claude plan, through [pi-claude-bridge](https://github.com/elidickinson/pi-claude-bridge): it runs Claude Code through Anthropic's Agent SDK with Claude Code's own system prompt first and Pi's appended, while Pi keeps the agent loop, tools, approvals and compaction. Anthropic decides plan vs. third-party (extra usage) billing largely from the system prompt; this shape bills the plan (tested 2026-11-15 with the full Pi setup: codemode, MCP, every extension).

- **Only this instance loads the bridge.** `ag-t3 setup` installs `pi-claude-bridge` at a pinned version into `~/.local/share/pi-claude-bridge` (bump `CLAUDE_BRIDGE.version` in `ag-t3` after reading the changelog and retesting billing), and the instance passes `-e` with its path as Pi launch args. Other sessions never load it.
- **Login and environment.** It shares `~/.claude-personal` with "Claude · personal" (`CLAUDE_CONFIG_DIR`; same login), blanks the TrueFoundry variables, and stores sessions in `~/private-chat/pi-sessions` like `piPrivate`, so personal work stays out of the company trace sync. Claude Code's own transcripts go to `~/.claude-personal/projects`.
- **Only personal-plan models.** Its picker shows only `claude-bridge/…` models, with `claude-bridge/claude-opus-5-5` as its favorite. The instance sets `AG_PI_SUBSCRIPTION=claude-bridge`; there `truefoundry-only` keeps the session on a `claude-bridge` model and refuses to send a prompt while none is selected, and `policy-fallback` never moves it to TrueFoundry. A Pi started from it without the bridge (a subagent child) is an ordinary TrueFoundry session. `ag-t3 doctor` checks the instance, the pinned install, the picker, and that its threads stay on `claude-bridge`.
- **If Anthropic reclassifies it**, requests fail with "Third-party apps now draw from your extra usage" (nothing is charged while extra usage is off). The bridge's predecessor here, [pi-claude-code](https://github.com/earendil-works/pi-claude-code), rewrites requests on the wire and hit exactly that ([issue #53](https://github.com/earendil-works/pi-claude-code/issues/53)); don't use it. Never use Pi's own Anthropic `/login` either.

**Personal Claude.** `claudePersonal` ("Claude · personal") is T3's own Claude Code driver (`claudeAgent`), not Pi, signed in to Nathan's personal Claude plan, so it bills that plan's limits. Its favorite is Opus 5.5, next to TrueFoundry Opus under "Pi · work".

- **Fallback.** Kept next to the personal Pi lane in case the bridge breaks; it's Claude Code itself, not Pi.
- **Its own login.** The instance uses `~/.claude-personal` as `CLAUDE_CONFIG_DIR` (its `homePath`) and blanks `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` and `ANTHROPIC_API_KEY`, which the shell points at TrueFoundry. Sign in once per host with `env -u ANTHROPIC_BASE_URL -u ANTHROPIC_AUTH_TOKEN CLAUDE_CONFIG_DIR=~/.claude-personal claude auth login --claudeai` (with those variables set, Claude Code reports itself signed in through TrueFoundry).
- **Ag's Claude config.** `ag-t3 setup` links ag's Claude Code `CLAUDE.md`, `settings.json` and skills (`claude/dot-claude`) into `~/.claude-personal`; `~/CLAUDE.md` loads from the home directory as usual. Pi's extensions and Pi skills don't apply there.
- **Off the record.** Its transcripts live in `~/.claude-personal/projects`, which nothing syncs. The `lane` rules leave it alone (they only move `pi` ↔ `piPrivate`), and `ag-t3 doctor` doesn't pin its threads to TrueFoundry. Doctor checks the instance and that its login has a Claude plan. Setup removes the retired `piWork` instance.

**OpenRouter Claude models need a `models.json` entry.** `~/ag-personal/pi-models.json` overrides the `openrouter` provider with OpenRouter's OpenAI-compatible `/api/v1` endpoint (for Fable 5), and pi applies that base URL to catalog models that use the Anthropic API, so every call 404s. Give such a model its own entry with `api: anthropic-messages` and `baseUrl: https://openrouter.ai/api` (Opus 5.5 has one). Haiku 5.5 is also on TrueFoundry (`truefoundry/anthropic-primary/claude-haiku-5-5`).

`ag-t3 setup` enables both Pi provider instances (`providerInstances.pi` and `providerInstances.piPrivate`: driver `pi`, Ag's `~/.local/bin/pi`, the private one with its session-dir environment; `pi` is labelled "Pi · work"), the personal Pi lane and personal Claude instance above, configures a non-Anthropic title-generation model, applies the model preferences above, then runs `doctor`; bootstrap calls it on every host setup, and it's safe to rerun after an upstream sync. `ag-t3 doctor` checks the live Pi catalog, the configured provider instance, visible non-TrueFoundry models, expired OAuth access tokens and thread selections, reporting rather than silently substituting. `ag-t3 new --model` refuses models outside TrueFoundry.

## What the fork had that upstream lacks

- **Automatic lanes:** No pre-message check against `ag-rules` to auto-switch to the private lane.
- **365-day pairing:** Upstream paired logins last 30 days instead of 365.
- **2-hour idle session retention:** Upstream unloads idle Pi, Claude, and Codex sessions after 30 minutes instead of 2 hours. The next message waits ~2 to 3.5 seconds for Pi to start.
- **Quick entry:** Pressing both Command keys in the Mac app is gone.
- **In-app deep search:** `Option-Command-K` in the app is gone (`ag-deepsearch` still runs for `ag-dash`).
- **UI tweaks:** Vim-style normal mode keys, the single-workspace sidebar, and reveal active chat are gone.
